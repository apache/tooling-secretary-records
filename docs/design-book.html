Board Agenda Tool · design book

One decision, made once.

BAT has 26 pages, four table systems, 18 button variants, 51 icons and 27 distinct type treatments. Almost none of that variety carries meaning — it is the residue of each page being built on the day it was needed. This book fixes the vocabulary so that the next page is a composition rather than an invention.

Twenty-three chapters in six parts, every assertion measured against the running product. Companion to issue #555, which argues how the agenda should behave; this book is the material it is built from. Chapter 23 records what building it changed.

Part I Foundations

What everything else is measured in: the palette, the type scale, the spacing step, how things move, and how they are drawn.

01 Why a book, and where its numbers come from

Issue #555 argued how the agenda should work. This is the layer underneath: the pieces every page is built from, so that argument can be implemented without re-deciding typography on each screen.

Everything asserted here was measured, not eyeballed. A throwaway Playwright probe walked all 31 rendered surfaces — every server-rendered page, every tab of the agenda app, and one item of each element type — and recorded the computed type, colour, icon and link treatment of each, plus what overflows a 390 px viewport and which controls fall under the 24×24 target minimum. The probe ran against the newest agenda in the fixtures, 2025-06-18, as the Secretary, the Chair and a plain director. A second probe read every table and list on those pages column by column, counting distinct values, so that §20 and §21 could judge which data each page is actually carrying rather than how it is dressed.

The reading the resolutions do not have — a JIRA resolution neither list classifies — takes the outlined ink of §08 and quotes the resolution rather than guessing at it.

A chip marks an exception, not a fact

This is the rule that keeps the table above from growing. A chip says this departs from the normal state and may need you. Missing, flagged, awaiting approval, in progress: all exceptions. A person's office, a committee's type, a date, a count and a role are facts, and facts are carried by type and position — a labelled column, secondary type, a heading — never by a coloured chip.

The test is whether the value is true of every row. If every row has one, it is a column. “Board Chair” against a director is a fact about that seat and belongs in an office column; “Vacant” is an exception and takes a chip. Getting this wrong is how a status vocabulary stops meaning anything: once roles are chips, a reader scanning for something wrong has to read every chip to find out it was only a job title.

Colour is never the only carrier — but the word may be hidden

Every chip is icon + count + word, and it always carries all three in the accessible name. What varies is how much of it you can see. Below the medium breakpoint the word is visually hidden — clipped, not display: none, so it stays in the accessible name and in the tooltip — leaving icon and count. That buys back roughly half the width of a chip row, which on a 390 px queue row is the difference between the title fitting and not.

The item view always spells it out: the index is a scan, the item is the truth, and you are never more than one keystroke from the full wording. Do not extend this to controls. A chip is a read-only label in a list whose vocabulary repeats on every row, so it is learnable. A button that does something is not: icon-only controls keep their visible label except where §06 explicitly allows it.

Neutrals

Greys are biased violet toward the navy rather than pure, so that a card edge next to a navy heading reads as part of the same family. Backgrounds run --paper (the page) → --surface (cards, rows) → --plate (headers, wells). Three levels, no shadows: BAT is a dense reading tool, and elevation costs contrast it cannot spare.

What does not change is the mapping: navy still means structure, red still means missing, and the table of states above is read the same way in both. What changes is which side of a pair is the ground. In the light theme --navy is a fill carrying --surface text; in the dark one it is a pale periwinkle carrying that same token, which is now the dark one. So a rule written against the tokens is already right in both themes, and a rule that names white or black is the one that is about to be wrong in one of them — which is what the chip borders, the counts on a chosen queue and the six hand-picked button shades all were.

The two text-safe variants go back to the hue. --flag-text and --gold-text exist to buy contrast against white; against #141219 it is the undarkened hue that has it and the darkened one that does not, so in the dark theme each resolves to its own hue. --gold-text (#8A6003; --bat-amber-text in the product) is new with this change — the awaiting chip had been setting its words in a hex of its own, which is the same 1.9:1 problem --flag-text was added for.

Three things are deliberately the same in both. The ribbon keeps its six-stop gradient, being a decorative strip rather than a source of tokens. The mark keeps the four inks of the feather, which are not ours to re-choose. It is a gradient across all four rather than a flat fill, which is what carries it on a dark ground — the purple stop alone is 1.9:1 on #221F2B, and a logo is exempt from the contrast floor for exactly this reason. And paper is white whatever the screen is doing, so @media print is the light theme in both.

The one that matters: report bodies are prose

38.7% of all text in BAT is currently set in SFMono-Regular at 14 px. That is not because BAT is full of code — it is because renderMarkdown defaults to on, and the rendered markdown is emitted into the same font-monospace text-nowrap overflow-x-scroll container that was built for the raw view. So a PMC's prose is typeset as if it were a diff.

Prose face, measured column
Apache Camel had a very active quarter. Two releases went out and the PMC added three committers. There are no board-level issues.

Rendered markdown, 16 px Open Sans, wrapped at a readable measure. Headings, lists and emphasis get real typographic weight.

Raw face, no wrap
Apache Camel had a very active quarter. Two releases went out and the PMC added three…

Correct only for the raw toggle, a diff, or minutes: text where column position and exact characters carry meaning, including the 78-character marker.

The switch is the existing renderMarkdown flag, unchanged. What changes is that the two branches stop sharing a container: rendered markdown gets a prose container, raw text keeps the monospace scroller.

A resolution is prose too. The raw face is right for the source view, a diff and the minutes — text where column position and exact characters carry meaning. A resolution is none of those: it is clauses, and a director reads it one paragraph per clause at the width of the pane. It was drawn in the fixed-width box only because supportsMarkdown was written as report-or-discussion.

It is also the element whose source view has the clearest job, which is why the two are allowed to look as different as they do: the raw view is the wording that will be moved, voted on and copied into the minutes word for word, and the marker over it says so in those terms rather than in a report's.

Measure

Running prose wraps at 66 ch. Report bodies, minutes and documentation all obey it. Tables, raw text and diffs are exempt and scroll inside their own container instead — the page body never scrolls sideways.

Numerals

Anything that lines up in a column — element numbers, counts, sizes, revisions, dates in a table — sets font-variant-numeric: tabular-nums. The agenda's element-number gutter is already a fixed 44 px; tabular figures are what make that gutter actually align.

04 Space & surface

A 4 px base step, three surface levels, and two radii. Density is the point: this is a tool people read 74 reports in, not a marketing page.

Spacing steps

4 · 8 · 12 · 16 · 24 · 32 · 48 · 64
Row padding 8/12. Card padding 16. Gap between cards 16. Section break 32.

Radius

3px on controls, chips, inputs and table wrappers.
6px on cards and panels.
Nothing else. No pills except a count bubble.

Borders, not shadows

1 px --rule for structural edges, --rule-soft between rows. Shadows are reserved for genuinely floating layers: modals and the sidebar toggle.

Layout with gap

Sibling groups are laid out with flex or grid and gap. No per-element margins that collapse or double — which is what produced the current mb-2/mb-3/mt-2 drift across otherwise identical cards.

Delete the universal reset. app.css opens with * { margin: 0; padding: 0 }, which loads after Bootstrap and erases its entire spacing scale — then re-adds margins for h2, h3, p, ul and form by hand. Every spacing surprise in the product starts here. The reset should be scoped or dropped before anything else in this book is implemented.

05 Motion

BAT has four transitions, all of them transition: all, and no easing vocabulary. Motion here has one job: explain where something went.

This is a tool people operate at speed — 74 stops in a queue, arrow key held down. Motion that delays a state change is a tax paid on every one of those stops. So the rule is narrow: animate to explain a spatial relationship, never to decorate a state change. A drawer slides because it came from an edge. A chip does not fade in because its report became flagged.

Durations & easingthree, and no others
Instant · 0ms
state, selection
Quick · 120ms
hover, focus
Move · 200ms
drawer, sheet, disclosure
  • Instant for anything that reflects data: a chip appearing, a row leaving a queue, a count changing. The state is the message; a transition only delays it.
  • Quick, 120 ms, ease-out for pointer feedback — hover and focus. Named properties only (background-color, border-color), never all.
  • Move, 200 ms, cubic-bezier(.2,0,0,1) for things that travel: the sidebar drawer, the presentation sheet, a disclosure opening. Transform and opacity only, so it stays off the layout path.
transition: all is banned. All four in the product are all, which animates properties nobody intended — including width on the sidebar, which forces layout on every frame of a hover. Name the property. .no-transition, the existing escape hatch, then has nothing to escape.

Every rule above sits inside @media (prefers-reduced-motion: no-preference), not outside it with a reduce override bolted on. The reduced case is the default and the animation is the enhancement — which is also the honest reading of a governance tool whose users may be reading it in a meeting they are also chairing.

06 Iconography

51 icons are in use. Several mean the same thing in different places, and a few mean different things under the same glyph. One glyph, one meaning.

The drawing rules

  • 16×16 viewbox, 1.5–1.6 px stroke, round caps and joins, no fills except where a shape is solid by nature (the flag).
  • currentColor always, so an icon inherits the chip or button it sits in and needs no per-context variant.
  • Rendered at 12 px inside a chip, 15 px inside an icon button, 16 px inline with UI text. No other sizes.
  • aria-hidden="true" when a word is beside it; an accessible name on the control when it is not.

Glyphs with a fixed meaning

A glyph that stands for a kind of thing means that kind of thing everywhere. Two are settled, and they are the two that appear beside a name:

07 Information types

BAT shows the same eleven kinds of thing over and over. Each gets exactly one rendering, everywhere it appears.

Person

Today a person's standing in the Foundation is encoded in font weight alone: bold for a member, italic for emeritus, light for a non-member, lighter for deceased. That is invisible in a table of forty names, and it is the definition of a distinction that cannot survive a screenshot, a printout, or a low-vision reader.

A person gets two renderings, and which one you use depends on whether the row is about them. Collapsing to a single treatment is what would break the visual language: a two-line block is right where the person is the subject, and doubles the height of a twenty-row table where they are merely an attribute of something else.

08 Status & the chip

One component carries every exceptional state in the product, across 1,868 instances. This is its anatomy, its vocabulary, and the one rule that stops the vocabulary growing.

Anatomy

The way bg-warning came to mean three things is that nobody had to ask. 09 Links

Eight different link treatments are rendered today, including a hardcoded #0000ee that predates the palette entirely.

  • In prose: navy, underlined. Underline is not optional — it is the non-colour carrier.
  • In a table cell or a queue row: navy, underline on hover and on focus. A row of forty underlined names is noise; a cell that never underlines is undiscoverable.
  • Leaving BAT: always marked with a trailing outward arrow and rel="noopener". 38 of 41 external links are marked today; the remaining three are inconsistency, not intent.
  • Dressed as a button: only when it acts on this page. A link that navigates is a link.
  • Visited: not distinguished. In a queue you traverse repeatedly, a visited colour would encode “you have looked at this” — which is what the read state already means, properly and per-user.
Delete .item-link. It hardcodes #0000ee, the 1994 browser default, and appears 39 times. It is the clearest single marker of where the interface stopped having a palette.

10 Voice & tone

BAT writes for directors, chairs and the Secretary in the middle of governing. The register is a colleague who knows the bylaws: precise, unhurried, never chatty.

Rules

  • Name things as the board names them. Special order, resolution, roll call, pre-approval, shepherd, action item. Never invent a friendlier synonym for a term of art, and never surface an implementation word — a reader has uncommitted changes, not a pending-changes array.
  • A control says what happens. Approve, Commit, Post report, Stop meeting. Then the confirmation says it happened, in the same words: Approved, Committed. Not Success!
  • One action, one name, everywhere it is spoken. The button, its tooltip, the dialog it opens, the confirmation and the test id are all the same words.
  • Sentence case everywhere except Label type, which is uppercase by styling and sentence case in the markup. Title Case On Buttons reads as a brochure.
  • No exclamation marks, no apologies, no emoji. The repository already forbids emoji in commits and issues; the interface is the same product.
  • Second person for the reader's own state — “visible only to you”, “74 left to approve” — and third person for facts about the agenda.

Rules

  • Every control has a real <label> tied by for. Placeholder text is not a label — it disappears exactly when the reader needs it, and fails contrast in every browser default.
  • One column. Forms sit at the prose measure. Side-by-side fields halve the reading width for no gain and break on a phone.
  • Required is marked on the field, not signalled by its absence. required plus a visible marker plus aria-required.
  • Validate on blur, re-validate on input, never on keystroke first. Telling someone their email is invalid while they type the third character is noise.
  • The error is beside the field, tied with aria-describedby, and the field carries aria-invalid. A summary at the top of the form as well, when more than one field failed.

  • Destructive submits name the object. “Terminate Apache Foo”, not “Confirm”.

Specific to BAT

  • The 78-character rule is a form constraint. LongLineTextarea already marks over-long lines while editing, with the same amber the read-only view uses.   • Textareas that become agenda text are monospace — they are edited against a column limit. Textareas that become prose (a comment, a note) are not.
  • The seven raw checkboxes in Pending Changes and elsewhere do not inherit the component's focus, sizing or label handling. They are the 16 px targets in §17. One component.

14 Feedback

Loading, empty, error and notification are one family: four answers to “why is there nothing useful here?” Today they are answered by a spinner, five different words for nothing, and a toast that vanishes in four seconds whether it said “saved” or “failed”.

Loading

  • Under 200 ms: show nothing. A flash of spinner is worse than a pause.
  • In place, not instead. A control that is working keeps its size and says what it is doing (§11). Replacing a button with a bare <Spinner> — the current pattern in Pending Changes, Draft Agenda and six other components — makes the layout jump and removes the label that said what was happening.

State that is only yours

Pending changes, read marks and personal notes are per-user and invisible to everyone else. They must always be distinguishable from facts about the agenda: hence the dashed pending chip, and hence read being a quiet read rather than a filled success badge.

It applies inside a tally too, and that is the case most easily got wrong. The approvals card and the consent card list people by name, and your own name joins the list the moment you press the button — it is your copy of the agenda you are reading, and nobody else can see it yet. So a name in one of those lists is not evidence that the board has it. A segment that is there only because you staged it is striped, and the sentence under the tally says so in words. Solid means committed and on the record; striped means yours, and not yet. It costs no hue: the fill stays the one that already means agreement.

The converse is striped too, and it is the one easily missed. Staging an unapproval takes your name off the list on your own copy — and everybody else goes on seeing a solid approval, because the record still has it. Left alone, the card would quietly drop a name the board has. So the list is what the record says together with what you have staged, your segment is striped either way, and the sentence under it carries the direction: “Yours is not on record until you commit it” against “Yours is still on record until you commit its removal”. The stripe means the segment is in flux; it never means which way on its own, which is why the sentence is not optional.

A consent has only the first reading. Withdrawing one takes the staged change back rather than staging a second, so a consent is never on the record and staged for removal at once.

17 Accessibility

Zero prefers-reduced-motion, prefers-contrast or aria-live rules exist today, and seven aria-labels across the whole product. This is the largest gap in the book.

Document outline

The agenda page has 44 <h1> elements, all carrying class="modal-title fs-6" and none of them in a modal, while the actual page title is an <h4>. Meanwhile real modal titles are <h5>. To a screen reader the page has no structure at all.

  • h1 — the page title, once.
  • h2 — a major region: a card, a tab pane, a dialog.
  • h3 — a titled block inside one.
  • Never choose a level for its size. Size comes from the type role.

Comfortable mode

A stated goal is that someone with poor eyesight can still work the tool. That means the layout survives being scaled, rather than a separate large-text skin:

  • Every size in §03 is set in rem, so the browser's own text size works. Twelve hardcoded px font sizes break this today: nine in app.css, two in AgendaElementView, and one in RollCallSectionView. The browser's default font size is honoured everywhere except the report body, the badges and the diffs — that is, except the text you came to read.
  • Content reflows to a single column at 320 px equivalent without horizontal scrolling (WCAG 1.4.10), and survives 200% text zoom (1.4.4). See §18 — today neither holds.
  • A Reading comfort group in the settings modal that already exists, with three steps scaling from a root that inherits the browser's own setting: Compact 0.875 / Comfortable 1 / Large 1.25. It also opens row padding one step, restores every clipped chip word (§02), and expands icon-only controls to icon + word. It changes spacing and type only — never which controls exist.
  • prefers-contrast: more thickens rules to 2 px, drops chip tints in favour of solid borders, and removes the muted grey from secondary text — bound to the media query as well as to the switch, so a stated system preference is honoured without anyone finding the setting.
  • Preferences persist in localStorage, not sessionStorage. Every preference is currently lost with the tab, which is tolerable for “which queue do I start in” and wrong for “I need larger text”.
The keyboard model is an accessibility feature that is currently hidden. Ten queues and eleven bindings mean the entire review can be done without a pointer, and nothing on screen says so. The queue switcher prints its keystroke beside every entry, which makes the discoverability fix and the accessibility fix the same work.

Targets and focus

  • Interactive controls are at least 24×24 px. The measured failures are real controls, not prose links: the queue radios at 13×13 and the reminder switches at 16×16.
  • :focus-visible gets a 2 px accent ring at 2 px offset, on every control, in both themes. There are two focus-visible rules in the product today.
  • Focus moves to the item bar heading when an item opens, and back to the row you came from when it closes.

Announcements and motion

  • The websocket notification stack is aria-live="polite"; errors are assertive. Currently a director gets no announcement at all when a change lands or fails.
  • Every transition sits behind prefers-reduced-motion. The sidebar's transition: all 0.3s and its translateX hover are the two that matter.
  • Done, 2026-09 (#886). Both themes are designed, not inverted — the tokens in §02 were the mechanism, and the palette is set out there. A reader who has told their machine they want dark gets it without finding the setting, which is the same argument this list makes for prefers-contrast above; Appearance in the preferences dialog is for the reader whose answer differs from their machine's.

19 Print & offline

The board's workflow is online end to end, and nothing in this chapter is a gap being filled. It exists for one case the online workflow does not cover: reading and marking up an agenda with no connection — on a plane, before a meeting you are preparing for away from a desk.

So the goal is not a filing copy or a record. It is a take-away: the reports, enough status to know where to spend the attention, and room to write. There are zero @media print rules in BAT's own stylesheets today, so what comes out of a browser is the screen with its chrome, its queue switcher and its colour-coded chips rendered meaninglessly in grey.

The “Formatted agenda” link is the closest thing that exists — a plain-text rendering of the whole agenda with the reader's pending changes applied. That is the right instinct for a take-away and the wrong output for this purpose: it discards every status that tells you which of 74 reports to read first, and it leaves no room to annotate.

There is no round trip. Notes made on paper have to be typed back into personal notes or comments when you land. The print cannot fix that, but it can make it cheap: element numbers set large and unmissable, so a scribble against 6B is one keystroke from the right item when you are back online. Designing for the return journey is most of the value here.

Rules

  • Room to write. This is the requirement everything else bends to: a generous outer margin, and space after each report rather than reports packed to the page. A take-away with no white space is a worse artifact than a longer one.
  • Status becomes an outlined label, not a tint. A take-away is almost always monochrome, so every chip prints as its word in a hairline box. Colour that survives is a bonus, never the carrier — the same rule as §02, tested by a medium that may have no colour at all.
  • Element numbers are set large. They are the index back into the tool (see above), so they get more weight on paper than on screen, not less.
  • Chrome does not print. Sidebar, ribbon, queue switcher, tab strip, notification stack, every button. If it acts, it does not print.
  • Report bodies print as prose at 10.5 pt with 1.4 leading, and the raw view prints monospace at its real column width — the 78-character rule is a fixed-width constraint by origin.
  • Page breaks respect the structure. break-inside: avoid on an element and its body; break-after: avoid on a section heading, so no agenda item is orphaned from its number.
  • Every page says which revision it is. Source file, revision and the date it was taken, in a running footer. The agenda moves while you are offline, and the one thing a returning reader needs to know is whether what they annotated is still current.
  • Links print as text. An external URL prints after its label; internal hash links print as the element number they point to, not as #camel.
  • Private blocks print, keeping their enclosing box so the boundary is unmistakable on paper — and the footer says the sheet contains board-private material, because a take-away leaves the tool's access control behind.

What to take, not everything

Printing 137 elements to read four is the wrong artifact. The take-away is generated from a queue (§16), which the tool already knows how to compute: print what is missing, what is flagged, what you have not approved. The queue you are in becomes the document you take, which makes this feature almost free — the selection logic already exists and is already the thing the reader was working through.

Lowest priority in this book, and worth keeping anyway. Nothing in the current workflow depends on it, so it sits behind every other chapter. It earns its place for two reasons: the offline case is real, and print is a useful honesty test for everything else — whatever survives losing colour, hover, motion and interaction was information, and whatever does not was decoration. If a state cannot be printed, §02 got it wrong.

22 Order of work & governance

Sequenced so that each step is independently shippable and the early ones make the later ones cheaper.

  1. Tokens and the reset. Land §02–§04 as custom properties; scope or delete * { margin: 0; padding: 0 }; self-host the two faces. Nothing looks different yet except spacing stops drifting.
  2. Bugs found while measuring, in this order. They are not design work and should not wait for it:
    • Committing pending changes commits the wrong ones. checkedPendingChanges() is pendingChangesChecked.filter(c => c).map((_, i) => i) — it maps over the filtered array, so it returns 0…n-1 rather than the positions of the checked boxes. The server indexes its stored list positionally (enumerate(pending_changes.changes)), so unchecking anything but a trailing run commits and reverts the wrong changes. Uncheck the first of three and you commit changes 0 and 1 — including the one you just excluded. It is only correct in the all-checked default, which is why it has survived. Same call feeds Drop and Preview diff. Nothing covers it in e2e/tests.
    • The :global(.content-box h1, h2) selector-list leak, which makes bare h2/ul on any page loading that chunk take the report body's type. Prerequisite for touching the report pane.
    • n s selecting the Shepherd queue even when that queue is hidden, stranding the user on an empty index with no filter selected.
    • The tasklist's severity sort ordering info above warning alphabetically (§21).
  3. Status vocabulary. The eight chips. One file, immediate legibility win across every list in the product.
  4. Report bodies as prose. Split the markdown and raw branches into separate containers.
  5. Queue switcher and item bar. Removes the 289 px overflow and makes the tool usable on a phone.
  6. Document outline and focus. Heading levels, aria-live, :focus-visible, target sizes.
  7. Comfortable mode and prefers-*.
  8. Tables. Tokenise Grid.js; fix the three remaining overflows.
  9. The data itself. §20–§21, page by page. Officers & Directors, Users and Committees first: they share the person and role types, so they are one change spread over three pages rather than three changes.
Steps 1–3 are worth doing even if nothing else in this book is adopted: they cost little, they are invisible to workflow, and they remove the ambiguity that makes every subsequent design question expensive.

How the system changes

A design system that cannot be extended gets worked around, and a system anyone can extend stops being one. Three gates, matched to what is actually at stake:

ChangeNeedsBecause
Using the system — a new page from existing widgets, a new column, new copy Nothing. Build it. This is the system working. If composing a page requires a discussion, the book has failed.
A new configuration — a widget variant, a new empty state, a new field type A note in the PR saying which existing thing it extends Cheap to review, and the note is what stops two people inventing the same variant twice.
A new token, hue, chip, icon meaning or type role An issue, and a change to this book in the same PR These are the things that decay. bg-warning came to mean three things because no gate existed — each addition was locally reasonable.

Rules that keep it honest

  • The book changes in the same commit as the code. A design book that documents last quarter's product is worse than none, because it is trusted.
  • New states earn a chip by the test in §08 — exceptional, actionable, not already implied by a column. Failing any of the three means a column.
  • Tokens are named for meaning, not appearance. --stop, not --red; the day the red changes, every use of it is still correct.
  • Class names are scoped to their component, never generic. .bat-chip-count, not .n. A short generic name collides the moment two components nest, and the collision is silent — equal specificity means source order decides, so it breaks for whoever's rule happens to come second. This is the same failure as the app's :global(.content-box h1, h2) leak, and an earlier draft of this very page had it: the chip's count span and the queue row's element-number gutter were both .n, so every count inside a row silently inherited a 44.8 px fixed width and the gutter's monospace face.
  • Nothing new gets a hardcoded px font size or a transition: all. Both are lint rules, not conventions — stylelint is already in make check.
  • Every UI change ships its two layers of tests (vitest and Playwright), as the repository already requires. A widget without a test is a widget that will drift.
  • Re-run the audit. The two probes behind this book are a hundred lines of Playwright each and produce the numbers in §01 and §20. Run them once a release: the count of type treatments, button variants and chip meanings is the system's health, and a rising number is the only early warning there is.

23 What implementation changed

Sixty-five things the book got wrong, left out, or stated too loosely to build from. Each is now what the product does.

Corrections

The book saidWhat it isWhy
Four button roles, reached by restyling the six Bootstrap variants and leaving the class names as aliases (§12) Four roles at the call site: primary, secondary, danger, link Mapping by variant name rather than by what a button does was wrong. Most color="warning" buttons are labelled Reflow - a text formatting utility - so restyling warning as destructive painted about fifteen harmless buttons red. Classified by behaviour instead: Drop, Delete and Drop for this session are destructive and were not marked as such before.
The eight type roles, offered as tokens (§03) The scale enforced: headings resolve to it, and Bootstrap's fs-* and .small are mapped onto it Defining tokens and leaving every component free to pick its own size is how 27 treatments accumulated. Offered, the count went up to 30; enforced, the product renders six sizes and four weights.
Four queues pinned, a fixed number of slots (§16) As many as the row's width allows, measured; the remainder behind the menu, and no menu at all when they all fit A fixed count is a guess that is wrong at both ends: it wasted a 2400 px screen and still overflowed a phone at a large text size. The row measures its labels off screen and fits what it can, so the same control suits a phone, a tablet and a wide screen without a breakpoint for each.
Some queues pinned, the rest behind a menu (§16, and the row above) Being tried, not settled (#565): one control naming the queue you are in, opening all of them Fitting what a width allows means what a director sees is decided by the screen they happen to have: at 1280 px Mine 0 and Notes 0 held pinned slots while Missing 20 was behind the menu, and on a phone nine of twelve queues were. One control is 186 px in every queue at every width and text size - measured against the widest name it could carry - and the menu it opens sets name, keystroke and count in three columns, which is the first time the keyboard model appears on screen at all. What it gives up is the ambient reading of several counts at once, which is why it is a trial rather than a replacement.
The queue switcher wraps (§09, §18) Fixed width at every size: four queues pinned, the rest behind one menu Wrapping was never the requirement - fitting without pushing the page wider is. Wrapping only moves the cost from width to height, and it made the switcher grow every time a queue was added: at twelve it was two rows on a 1280px screen. A fixed number of slots decouples the control's size from the number of queues, and the menu holds the rest with their keystrokes intact.
The Info card, unexamined (§12) Attach and Author rows gone; a person links to the person Attach restated the element number - measured across the agenda, an attachment id is always the item's own suffix: 5-2 is attachment 2, 6-A is attachment A. Author repeated the title. What is left is genuinely new - submitter, audience, project - plus a block of links, which the book's own item-bar specimen already draws as icon buttons rather than a table row.
Person renderings, defined for the server-rendered pages (§07) The same two forms in Svelte, and a title's person is one of them The rule lived in macros/user.jinja and nowhere else, so the agenda - the surface that shows people most - did not follow it. A title's person is now icon plus name at UI weight, linked to their profile where the item is open (an index row is itself an anchor, and an anchor cannot contain one).

A flag chip carrying who set it The word is flagged; who flagged it is in the title, with a count when there is more than one A bare uid beside a title read as a name with no explanation, and made the chip a different width for every flagger - which is the one thing a column of status cannot afford. Every other chip says what it is and keeps its detail in the title.
Missing and missed-before, the same glyph in two weights (§08) Same hue, different glyph: a cross now, a clock before Filled-means-now and outlined-means-before is a fine rule until the word clips away below the medium breakpoint, and two red circled crosses sit side by side saying the same thing twice. The icon is the carrier that survives the clip, so it has to carry the difference.
An unlabelled switch over the report body No control in the view everyone reads in; a marker in the one they do not, a key, and a preference The rendering preference was a bare knob floating over the first line of the report whose meaning lived in a tooltip. Labelling it - Raw source, the label naming what turning it on does - fixed the reading of it and left the real problem: a control on every report, at the corner of the text, for something almost nobody does. So the preference decides what a session opens in, r flips it while you read, and rendered carries nothing at all. Raw carries a marker, which is the one place this design names the state rather than the action: a report that suddenly looks like source needs something on screen accounting for why, and the way back is that same marker. The key is printed on it, and again beside the preference - the two places a reader can find out the keyboard model exists. Pressing it does not write the preference: looking at what one badly rendered report actually says should not decide how every report looks tomorrow.
Draft state, as a sentence in the controls A chip on the element; the box that sets it is in the dialog that edits the wording, the same one the dialog that adds a resolution offers A w-100 wrapper took a whole line of the action row, which pushed everything after it onto a third tier - a special order's bar was a lone Edit, then this, then the icons. That a resolution is a draft is state, and state is a chip. It then spent a while as one button that kept its word, which was still a control in the row for something nobody does often: whether the wording is settled is a property of the resolution, so it is set where the wording is, and it is saved with it.
Edit, outlined in the destructive red Neutral, like every other control that stages a pending change Red is for what cannot be undone. An edit is staged like any other change, and it sat beside a Delete that genuinely is destructive, so the pair said nothing.
The date, with a weekday and a timezone (§20) 18 Jun 2025, 21:00 Every date in the product is already rendered in the reader's own zone, so the suffix restated the browser's setting - and on the agenda's own head it was part of what would not fit beside a drawer trigger, a mark and the agenda's age. The weekday goes from the page title too: the date there is specific, and which day of the week it falls on is a question a calendar answers.
The mark, merged into this design rather than integrated with it (§12) The two were made against different versions of the same head, and the head is where they meet The mark rides in the page head below lg, because the sidebar is a drawer there and the brand would otherwise be off screen with it. That head had just been cut from 89 px to 65 by taking eighteen characters out of its title - and a wrapping row answers a mark it cannot fit by putting the agenda's age on a line of its own, which spent the saving again. It does not wrap below md now, and the title gives way instead, as it does in an element's own bar: a trigger is its size and an age is four characters, but a date can end in an ellipsis and still say which meeting this is. The mark is 20 px rather than 24 on a phone - it is drawn rather than photographed, so its size is a choice, and at 20 the silhouette still reads.

Also settled here: the interface carries two ambers, #F7AE18 from the www.apache.org :root this palette comes from, and #F79A23, the fourth ink of the feather, which the mark is filled with. They are near neighbours and look like a typo of each other. Both are now named in the token block so that nobody reconciles them: the interface is the site's palette and the mark is the feather's.
The element header, designed on a committee report (§12) Eight corrections found by opening one of every kind in turn, and then all 86 committee reports A header that reads well on a committee report is wrong on the shapes that are not one. An element with no author and nothing true of it - call to order, adjournment, a special order, a discussion - drew the row for those anyway, 16 px of empty band under the title on five of fourteen; it is not rendered now, and whether there is anything to draw is asked of the chips themselves rather than guessed from a copy of their conditions. An action item's person is its assignee, which the row called Author while the Info card two inches below called it Assignee. The comments card counted this agenda's while listing earlier months' too, so a report whose whole history is older was headed Comments (0) above a list of them - it says both scopes now, rather than a total that would disagree with the chip on the same screen. The President, the Treasurer, the Secretary and the Executive Vice President are offices with pages of their own, and theirs were the only reports offering no way to reach them, because the check named two section types and they sit in a third. And an action item's Edit was still the destructive red, which its sibling control had already stopped being - as was a report's, the third of three. The broader pass, all 86 committee reports at 1440 px: every one 48 px for the title row and 48 for the row you work from, no title clipped, nothing overflowing. Two things it did find. The people row was 37 px on a report with nothing true of it and 39 on the next, because a chip is two pixels taller than the line of text beside it - so the report under it moved by that much on every step of a queue seventy-four long; it has a floor now. And Post wore the pencil, which is what Edit, Edit item, Edit action item and the pending chip all wear: it files a report that does not exist yet, so it takes a page with a plus. Post and Edit open the same dialog on the same field - what differs is whether there is a report yet, which is why one is filled and carries its word and the other is an icon among icons.
A control with an icon is the icon, the primary excepted by name (§12) Excepted by role: whichever control is the primary keeps its word. And an action item's button wears the glyph an action item wears everywhere else The exception was written as Approve and Unapprove, so Post - the whole point of opening a missing report - was a navy square with nothing on it, and Mark ready would have been the next one. It is the filled control that keeps its word, whichever control that is. The add-an-action-item button wore a checked box, which is also what read and approved would say; it takes the tasklist the chip and the expanded row already use. Bootstrap Icons has no tasklist-with-a-plus, and the button's own word and tooltip carry the add.
An Info card that renders for facts it no longer shows Info renders when it holds one; where else the element can be read about is a row of icon links on its title row Author and shepherd moved to the bar and the card kept rendering for them, so a committee report showed a card called Info containing a row labelled Links containing one link. They are on the title row now - roster, mail, past reports, statistics - which is where the book's own item specimen drew them, and which the title row has the width for once it is a row of its own. They are quiet and they are links: they leave the page, and the row below is the one that acts on the agenda. A card headed Comments (0) was the same non-news, and is gone too.
Agenda-level controls, in a card beside the agenda (§20) One right-aligned row above it - and above it means above, which took a second pass Add item, start meeting and the rest are page-level actions, and the book puts those on the page's own row. They had a third of the width for at most four buttons - and with a meeting running that column sat between the agenda and the presentation rail, squeezing the agenda to 575px of 1440. It is 862px now. The row was first built after the list rather than before it, which put Start meeting 6,076 px down the fixture agenda.
The item bar carries the title (§12) Two lines: number and title, then who answers for it - author and shepherd The shepherd left the index because it meant nothing to anyone but them; the open report is the one place it does, because that is where somebody is reading what the shepherd is meant to review. The chips move to the trailing edge with the controls, so the bar reads left to right as identity, state, actions.
View / Present, unstyled (§16) The same pill pair the queue switcher uses Present was outlined in the destructive red, which the book reserves for what cannot be undone - driving a meeting is not that. It is the same shape of choice as a queue, one of a set with the chosen one filled, so it takes the same treatment rather than looking like a different kind of control.
Arrow keys step the queue (§16) So does a swipe, on a touch screen The queue is the product's central idea and a phone had no way to move through one: no arrow keys, and the Previous button is at the foot of a report that can be two thousand pixels long. Dragging right reveals what is to the left, so it goes back. A gesture that starts inside something scrolling sideways belongs to that thing until it reaches its edge - reports wrap today, so this is for the wide content that does scroll.
The item bar is sticky, at the top (§12) At the top everywhere, under the page head where that is pinned too; on a phone the actions alone travel to the bottom edge Two things. The book's reasoning - controls parked at either end are off screen for most of a long report - argues for sticky, not for which edge, and on a phone the bottom edge is where a thumb reaches, so the actions go there. Only they travel; the number, title and chips stay with the element, because a strip carrying all of it costs three rows of a small screen. What stays at the top is the row that steps the queue, and below 992 px it pins at the page head's height rather than at the ribbon: sharing top: 0 with the head, which has the higher z-index, put the row behind it, where it read as having scrolled away. Stacked, they say different things - the head which meeting, the row which queue - and the offset is in rem so that it follows the reading size the head is built from, 65 px at the default and 81 at Large. A rotated phone is what found this: 915 px wide falls below the breakpoint, and 412 tall is where losing the step arrows costs most.
Page header: display title (§12) The agenda's title is its meeting date, and nothing else "Meeting Agenda for Wed, 18 Jun 2025, 21:00 UTC" spent eighteen characters saying where you already are - the sidebar entry is lit, the browser tab says Agenda - and those characters were what wrapped the title onto a second line on a phone. A meeting is named by its date. The head went from 89px to 65px there, and the agenda starts 24px higher.
A missing-in-past-months notice, as a full-width alert (§12) A chip, in the missing hue but outlined A committee that skipped a month is worth noticing even when it has filed this time, but it is not an alarm about this agenda - it was a yellow slab across the meta column saying four words. Filled says a state is true now, outlined says it was true before, which is a rule that adds no ninth hue and can be reused.
Queues and the View/Present switch, in one wrapping row (§16) One row that does not wrap; the queue row is the part that gives The queue row grows into the space left over, so in a wrapping container it pushed the mode switch onto a line of its own - a third tier of chrome under the tab strip and the status line, 83px where 46 would do. The queue row already measures what it can fit, so it is the one that should shrink.
Author and shepherd, both in the report's title (§07) The author stays inline; work that is yours is a chip, and a Mine queue collects it Every report read Airflow [Bolke de Bruin / Kanchana] - two people in a bracket, one of them a review assignment that means nothing to anyone but the shepherd. The book's own test says a value true of nearly every row is a column, not a chip; "this one is mine" is true of a handful, which is what a chip is for. One predicate in the model, so the chip and the queue cannot disagree: a report you wrote or shepherd, or an action item assigned to you.
Empty states, specified for panels only (§12) A queue that holds nothing says so, says what would put something in it, and offers the whole agenda The book wrote the rule for a panel and never applied it to the index, which is where it matters most: a filter that matches nothing rendered a blank page, with no way to tell an answer from a failure to load. Each queue has its own sentence, because "no reports are missing" and "you have made no notes" are different pieces of news.
The item bar: primary action, then icons and an overflow menu (§12) Built, without the overflow menu: a control with an icon is the icon, one without keeps its word The menu was written for a control count that does not exist. Measured across every item on an agenda, the most a viewer ever sees at once is eight, of which two are switches - six buttons fit one row at 390 px. The controls without icons are the ones particular to an element type, Vote and Attendance and Timestamp, and those are the primary action the bar is meant to name.
Rendering and acting, both in the controls (§12) Markdown sits at the top of the body; the bar holds only what acts on the element How a report is rendered is a reading preference, not an act on the agenda. It belongs with the thing it changes.
A revision timestamp, rendered in full (§20) How long ago, in the largest unit that is not zero: 12m ago, 5h ago, 3d ago A timestamp answers "when", which nobody asked. The question about a revision is whether it is the one you already read, and an age answers it in four characters instead of twenty-five. Repainted when it would change - on the minute while the age is in minutes, on the hour once it is in hours - since an agenda is left open for the length of a meeting. The exact time is in the popover; a date that stands inside a popover trigger takes no title, since the browser would draw its own tooltip beside it.
The age's exact time, said the way a list of revisions says it (§07, §20) One sentence, in the reader's own zone, in the popover and inside the link: Last change r1918863 (4 Aug 2026, 10:08 GMT+2) by striker An age is four characters and says nothing about what it is the age of. What was meant to answer that said r1918863 | striker | 2026-08-04T08:08:00+00:00 - three facts, no sentence, and a zone nobody reads in - and two readers asked what the time in the agenda header meant within a day of each other. A label beside it spends twelve characters of a phone's status row on something read once; a sentence in the popover spends none, and the same sentence stands inside the link where a screen reader reads it - the accessible name was "2h ago" and no more. Inside rather than over, as an aria-label: a name that replaces the visible text stops the control answering to the words written on it (WCAG 2.5.3), and the words written on this one are an age that repaints itself. The popover moves from the date to the link around it, because focus reaches a link and reaches nothing a tab stop cannot land on.
Status items, in no stated order (§12) Right to left by how much each asks of you: offline, pending, who else is here, then the link out. Anything with nothing to say is absent The row was ordered as it was written. "nothing staged" stated that nothing had happened, which is not status; a count of zero people is. On a phone the words clip to symbol and count, as chip words already did.
The drawer trigger, unplaced (§18) In the page head, beside the title Alone it took a row of its own: 48 px of an 844 px screen to carry one 40 px button, with the rest of that row permanently empty. The head is sticky below the drawer breakpoint, so the trigger stays reachable without spending a row on it.
A queue is a mode, held in memory (§16) A queue is a view with an address: #queue/flagged, and #queue/flagged/expanded when its detail is showing Retiring the tabs took the addresses with them. #flagged-reports and #commented-reports were links people held in bookmarks and mail, and they led to a view that no longer rendered - a blank page rather than a redirect. Those anchors now resolve to the queue that replaced them and rewrite themselves to its address. Naming a queue in the url also makes one shareable, which the tabs allowed and the queue model had quietly dropped.
Queues listed in no stated order (§16) Ordered by how much of a director's attention each is asking for Order did not matter while every queue was on screen. Once only the first few are, it decides what a director sees without asking, so it has to be a considered list rather than the order they were added in.
The reading switch floats over the body and costs no height (§12) The pane reserves its row, but only where the control exists It is opaque, and what is under it is the first line of the report - on 6-CF Xerces it sat on top of a sentence, which is exactly what not paying for the height was meant to avoid. An element that does not offer the control still starts at the top.
A chip is icon + count + word (§08) The word is clipped below the medium breakpoint, and restored at every width in Large The book had no responsive rule for the chip at all. Clipping rather than removing keeps the word in the accessible name, and the icon is the second carrier that makes it safe.
Nothing at all about the card (§12) A card header is Label type on a plate ground The book specified the header row of a list and of a table and never the card, which is the container both of those sit inside and the most-used surface in the product. Unspecified, it kept body type in the display face at regular weight: 41 px to carry the word Controls, reading as neither heading nor label. The rule it should always have had is the one already written for the list header.
A card header is Label type (the row above) And so is a heading inside one, which is where the rule went unenforced for fifteen headers Written for the header, the rule reached the headers holding bare text and stopped at the ones holding an <h2> or an <h4>, which set their own size over it: 36 px to carry the word Connected, against the 23 the same word costs on the card beside it. It was invisible for as long as it was, because the test that measured a card header measured one card, on one page, inside a tab pane that was mounted and hidden — so getBoundingClientRect() returned zero and every height passed. Building a pane only when its fragment asks for it (§20) made the card real and the measurement with it. The heading keeps its level, because that is the document outline's to decide; what it gives up is deciding its own size. #705.
The switch, specified by behaviour only (§12) Label in UI type, knob and label centred by flex Saying where the label goes and not what size it is left it at the body default: 16 px beside 14 px buttons, with the two centres 2 px apart because Bootstrap places the input with a float and a negative margin. Both were visible to the eye before they were measured.
Self-host the two faces (§03) Referenced from www.apache.org Vendoring OFL-licensed binaries brings NOTICE obligations into an ASF repository. For a Foundation tool the ASF's own host is first party, and both stylesheets declare font-display: swap, so nothing blocks on them.
Delete, in the row of controls (§12) In the dialog that edits the element, behind a second click, and honest about what it costs It was the one control in that row that clicking again does not take back - filled red, and on a phone a thumb's width from Read. Deleting an agenda item is rare, and every element that can be deleted but one has a dialog that edits it, so that is where it goes; the minutes of a previous meeting have no such dialog and keep it in the row. Two things were wrong beyond the placement. A delete that had worked reported a failure: the endpoint answers 200 with an empty body and the client read that as json, so every successful delete raised Unexpected end of JSON input and left the page pointing at an element that no longer existed. And the confirmation says you can revert it until the agenda is committed, which is true - a delete is staged like any other change - rather than borrowing the finality of a warning it has not earned.
A key printed in the queue menu, and nowhere else (§16) One treatment for a key you can press, wherever it appears The menu's keys had a style of their own, named for the menu; the esc in an element's footer has no style at all and takes Bootstrap's dark kbd. Now that a key is printed in three places - the menu, the preferences dialog and the marker on a report showing source - it is one class, so a reader learns the shape once. The footer's esc is still Bootstrap's and is now the odd one out; that is a separate change to a control this one does not touch.
The queue menu: name, keystroke and count in three columns (§16) Four. The mark each queue's meaning already wears, then the three Nine of the twelve glyphs are borrowed from where that meaning already appears - the flag on a flagged row and on the button that sets it, the bell on a board issue, the thumb on Approve - so the menu is read by shape before it is read by word, and no queue invents a mark of its own. Three are new, because their meaning has no glyph anywhere yet: the whole list, a special order, and the presentation order. That last one was the play circle for a while, which is the Present mode's own glyph two controls away - a mode you enter to drive a meeting is not the order the meeting runs in, so it is a stack with a play on it now. The keys were sized by their own letters, so n m was a wider box than n n and each began at a slightly different x: a column of keys that was not a column. Each of the four is a grid column now, so a glyph of a different width cannot shift the name beside it.
One text-safe variant, the orange's (§02) Two: --flag-text and --gold-text The amber is 1.9:1 on white, worse than the orange the exception was written for, and the awaiting chip is where its words are set. It had been setting them in a hex of its own, #8A6003 - in the product and in this page's own stylesheet, both. Which is the shape of the problem the dark theme found everywhere: a colour that is not a token is a colour with one theme's answer baked into it. The chip borders were eight alpha values of hues written out long, the count on a chosen queue was 75% white rather than 75% of the ground the fill covered, and the six hover and active shades of the three filled button variants were hand-picked darker hexes. Each is now derived from the token, so it follows the token into the other theme.
A draft chip on a resolution, a pencil, among the states that are not settled yet (§08) meeting only, the envelope struck through: the resolution is excluded from action without a meeting The state never said anything about the wording. All it does is keep the resolution from being put to the board by mail and consented to in writing (Bylaws 5.12), so it goes to the meeting; a resolution so marked is voted on there like any other. Called a draft, it read as unfinished. The checkbox says Excluded from action without a meeting, and the chip says where the resolution is decided instead. The agenda file keeps its draft: yes line. The calendar was not used because it is already the special meeting chip.

Sticky said of the item bar only, and nothing about where any of the moves between index and item land (§12) The index's controls row pins in the same place and on the same surface, and one rule governs every move between the two: the page moves only when the reader has been taken away from what they were on The book had already made the two one row - the queue control at the same x and within a pixel of the same y in either view - and then gave only one of them the pin, so the row a reader works from stays put inside an item and scrolls away on the index. What happens on the way in and out followed from the address rather than from a decision, and an address decides badly: a queue's address names no place in it, so leaving lands on the top of the page or at whatever offset the report ended at, and entering runs a fragment navigation, which the universal scroll-margin-top lands 98 px down a page that was already showing the item. The rule replaces all of it. Leaving brings the row you came from under the bar when it is not already on screen, whole and clear of it, and moves nothing when it is - a row a few hundred pixels down the index is one the reader can see, and fetching it to the bar scrolls the meeting's own heading off the top. Entering or stepping brings the element's head to the ribbon when it is above the window, and moves nothing when the whole element is already on screen. Below 992 px the page head holds the top instead, the same trade the item bar already makes, and the row clears the head rather than the bar. The one case the rule cannot be kept: an open item carries a viewport of tail so its head can always reach the top, the index carries none, so the last row of a twenty-row queue comes to rest where the end of the page leaves it - on a queue that short, on screen anyway.
What remains, said only in the switcher The open element carries it too: the queue you are stepping and how many are left, linking back to the list The book asked for a countdown (§07, §12) and the item bar shipped without one, so an element opened from a queue said neither which queue the arrow keys were stepping nor that there was an end to it. It is absent on All, which is not a queue being worked through.
A controls row and an item bar, both on screen with an element open (§12, §16) Three rows, each with one job - the row you work from, what this element is, who answers for it and what is true of it - and only the first one sticky. It is the controls row: the same queue control, at the same coordinates, plus the arrows and everything that acts on the element The index is not on screen while an element is, so the row above it had nothing to filter and no rows to expand - two tiers of chrome above the thing you came to read. Merging them into one flex row was the next mistake: a row that wraps has no defined states, and on 6-CF Xerces at 1280 px it produced orphan arrows, chips and controls wrapping to the left, and no two elements looking alike. Three rows with fixed jobs are 49 / 40 / 39 px at every width from 390 to 2400. The controls row is first, above the element's own title, and sticky: it is the row that does not change between the index and an element, and putting it under the title would have moved it down by one. It is measured - the control is at the same x and within a pixel of the same y in both views, at 1440, 1280 and 390, which is also why it has to be a fixed width (§16, #574), why Expand now follows it rather than leading the index row (89 px of sideways shift), and why the index row carries the same inset an element's first row gets from its card. Stepping leads and the actions trail, so Next and Approve - the two a director presses seventy-four times, one of which changes the record - are at opposite ends. The arrows are chrome, not controls: no border and no fill.
Nothing on how the step control gives way (§18) It does not have to: the queue control is a fixed width and the title is on a row of its own, so nothing squeezes anything. The arrows are there at every width Measured on four candidate layouts at three widths before the rows were separated. While the bar was one row, the tightest width was 992-1200 px - controls still in it, aside already stacked - and something had to give: the queue's name, or else the element's title, which is the one thing the row cannot lose. Three rows removed the competition. What still does not fit at 390 px is stepping in the bottom strip: two 44 px targets beside six controls overflowed by 68 px when they were tried, so the chevrons stay in the bar, where they cost 28 px each.
Previous and Next at the foot of the element (§12) One pair, in the bar. The foot keeps only the way out Two pairs of the same two actions, one of them in a place you reach only by finishing a two-thousand-pixel report - which is the wrong place for the control you press to leave before you have. The arrows are in the bar on every element, including in All, where there is no queue to count down and the agenda's own order is what you are stepping.
Status where the title happens to end Status holds the trailing edge of the row, and the list has a measure Chips began after the author's name, so 124 rows of status stepped diagonally down the page and no eye could run down it. A measure on the list is the other half: on a 2400 px screen a trailing edge is 1500 px from the title it belongs to, which is not a column worth having either. The cap is on the list rather than the row, so a row's ground ends where its content does.
A section heading's summary, unconditioned In a queue the heading counts the queue: (15 of 86) “86 this month; 18 are missing” sat above fifteen rows. The summary describes the section; what is on screen is the part of it this queue holds.
Nothing about the review order The one queue that is not in agenda order says so, above the list not-approved is sorted for review and shuffled within each group, so it runs 6-AI, 6-AW, 6-BN. Unexplained that reads as a list that failed to load in order rather than as the deliberate order it is.
One primary per view, stated but not built (§12) Approve is the filled control on a report, Post on a missing one; every other control in the bar is neutral A director's loop is approve, next, seventy-four times, and every control in the row looked the same - the action the queue is about had the same weight as Note. Once approved the pair inverts: Unapprove is an undo, and an undo is not a primary.
The chip's responsive rule, index only (§08) The item bar clips chip words below 1200 px too A tablet is where that bar is tightest: the controls are still in it, the aside has already stacked under the report, and four chips with their words plus six controls do not fit one line beside the title - the bar grew to three rows of a 768 px-tall screen. At Large the words come back at every width, as they do on the index.
The Bootstrap bridge Every Bootstrap colour resolves to a token; components it compiles as literals are overridden by name Bootstrap reads its utilities from --bs-*-rgb at runtime but compiles hexes into --bs-btn-bg and friends. Without the bridge the token layer is real and invisible - which is exactly what happened for several commits.
Retiring the tabs that were filters Flagged Reports, Comments, Shepherd and Personal Notes are gone; a Notes queue joins the ten, and Expand shows each row's note and comments in place They were the same list rendered again with their own copy of the markup. The only thing they added over the queue of the same name is the detail under each row, which is a display mode rather than a place.
The status line Who is connected, what you have staged and the formatted agenda sit above the tab strip; preferences move to the sidebar Status is what is true now, not where you are. As tab labels carrying badges they put status inside the row that says where you are. Preferences are the reader's rather than the agenda's, so they belong beside the name on every page.
Retiring the Summary card, the pending banner and two meta cards Gone Each restated something already on screen: the queue counts, the section headings, the pending chip, the Flagged queue, the special orders section. The banner was the fourth statement of one fact.
The sidebar as a drawer Below the large breakpoint it is off-canvas behind a menu button, full width for its labels §18 recorded that the labels were unreachable and never said what to do. A 55px rail of clipped icons is a seventh of a phone spent on nothing.
A Special Orders queue Third in the switcher; matches on the element being an order rather than on the section it sits in, and Expand shows each one's resolution in place Retiring the Special Orders card removed the one place a director could see them all at once, which matters most for an action without a meeting - an order raised between meetings, which they are asked to consent to and which does not sit in the Special Orders section. A queue restores that without spending a column, and matching by class rather than by section is what catches the ones raised elsewhere.
The wordmark is not a heading One line, Section type, a div rather than an <h1> It was a second <h1>, so the one-h1 rule held only inside main - which is also all the test checked. Stacked over three lines it cost 101 px to say the name of the product, and the collapse it appeared to serve never runs: the whole logo block is hidden when the sidebar collapses.
The presentation rail is a strip, not a column One row on the bottom edge at every width: who is presenting, the stop they are on, a switch to follow. The order is behind a disclosure on it, in a panel that is capped and scrolls The column listed the whole presentation order permanently, which is the agenda's own list a second time; the one thing it added was the line naming where the presenter is, readable while you have something else open. Below 992 px it became a band across the top of the agenda with no height of its own, so a hundred stops pushed the item under discussion off the bottom of a phone — during the meeting, which is when somebody is most likely to be reading on one (#661). §18 had asked for a drawer at one width and a bottom sheet at another; one treatment at every width is fewer things to get right, and the bottom edge is where the sheet was going anyway. The stop was marked text-danger, which §02's exhaustive table gives to a missing report; a stop in progress is go. The presenter was a primary badge, which said “exception” about the one fact on that row that never is one. On a phone the name is clipped as a chip word is: only the chair or the vice chair can hold the presentation, so it is the inferable half of that row, and 390 px carrying both wraps the strip to three rows - an eighth of the screen to say who is chairing the meeting you are already attending.
Focus must not read as state A switch shows state by knob position and track colour only Bootstrap swaps the knob to its primary colour on focus, so an unchecked switch that had just been clicked stayed blue and read as still on - reported from review, and made worse by the larger target §17 asks for.

Since closed. Secretary actions were post-meeting work that a meeting triggers rather than a view of one, read a tab at a time. They are /secretary now: every meeting that still owes something, newest first, its checklist under its date, and the meeting gone from the page when its last line is done - so an empty page is the answer rather than the absence of one. What decides whether a meeting is on it is not the same question as whether the next agenda may be built: a resolution parked for manual follow-up does not hold up an agenda, because waiting will never finish it, and it is squarely still the secretary's to do. The meeting's own checklist stays on its agenda at #secretary-actions, which is where the links in mail and bookmarks point. And with it moved, the tab strip had nothing left to switch between: it is gone rather than drawn with one tab in it. That row cost 42 px, and it cost 42 at every width - measured to the top of the first agenda row on the fixture agenda as the chair, at 390, 834 and 1280 px, by e2e/tests/agenda-chrome.spec.ts. A flat cost, which means the screen with the least room to spare paid the same as the one with the most: on a phone it is most of an agenda row. It was drawn only for the secretary, the chair and an admin, since nobody else had a second tab to switch to - so it is those three who get the row back. Four views still answer to a fragment - the checklist, presentation order, pending changes and the meeting - each reached from something that names it. #564.
And then the checklist itself. The page was right and the rows in it were not. Every line was an <h3> in a filled grey bar in the monospace face, carrying a navy needs action badge - so a checklist of twelve was twelve headings at the level of the four group headings above them, prose typeset as if it were a diff, and a chip on a value true of nearly every row, which is the rule in §08 read backwards. What replaced all three is one column. The rows are a list; the state moved into a gutter that holds a tick box where the work is BAT's to do, a filled check where it is recorded done, and nothing at all where the line is not the tool's to do - those rows carry their own control instead. An empty gutter rather than a hollow ring, which read as an unselected radio button: a control, which is exactly what it is not. The gutter is a grid column rather than the first item in a flex row, so the marks stay in one line down the card however far the words wrap, which on a tablet is two and three lines a row. The controls went to the rows they belong to. Drafting the summary and the minutes, and putting a special meeting's minutes to the next agenda, are not what the primary carries out, and they stood in the footer under a button that does something else - so the row that says the work now holds the control that does it, and the primary is the only thing left there. It says what it does and to how much: Carry out 5 actions, counted from the ticks, where Apply named no consequence and read a flag the server sent once. Clearing every tick left that button live, and pressing it wrote nothing and reported success. Three things went, none of them information: the Info group, which was three revision logs drawn in the shape of a task with no state on them and repeated once per meeting outstanding, and which is now one labelled row of links for the page; the General heading, which named nothing and on a meeting that decided no resolutions was one heading over the whole card; and three of the card's four primary buttons, since only the one the card exists for is a primary (§12). The cards themselves were .col children of one .row, so the page divided its width by however many meetings owed something - five of them were five columns a fifth of the page wide. They are a grid whose column count comes from the width a checklist needs.
And the two rows under it became one. With the strip gone, what was left above the agenda was still two tiers: the queues and Expand on one row, the page-level actions - Add item, Presentation order, Update Directors & Officers, Start meeting - right-aligned on another. They are at the trailing edge of the first row now, which is the row an open element's bar stands in place of, and which holds that element's own actions at the same edge. So opening one changes what the controls are about without changing where they are: measured in document space the two sit within a pixel of each other, where before they were a row apart. Nothing overflows at any width from 390 to 1920 px - the queue switcher already measures what it can fit, and it is the part that gives.
Below 992 px the actions leave the row for the bottom edge, in the treatment §18 already puts an open element's controls in, and for the same two reasons: it is where a thumb reaches, and it is the screen that can least afford a row above the reading. They are icons there, on the bar's own rule (§06) - with the words in, four of them wrapped to two rows, which is the thing moving them off the top was for. The words are clipped rather than removed, so the accessible name is unchanged and Large brings them back.
